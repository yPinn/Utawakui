# 中日韓歌詞對齊實測、品質檢查與漸進環境選型

本文保留當輪研究與分母；目前跨批次選型及未決項集中在[研究結論](lyrics-alignment-summary.md)。

本次研究的採用範圍與實作先後，見[研究收斂與實作評估](lyrics-acoustic-segmentation-implementation-assessment-2026-10-19.md)。本文完整起訖結論不可當成後續 T1 詞塊起點任務的直接排名。

日期：2026-10-18。接續[現行實作與方法研究](lyrics-audio-alignment-evaluation-2026-10-18.md)及[第一輪實測](lyrics-alignment-pilot-2026-10-18.md)。本輪完成實際模型推論、既有分離器消融、活動／重複句／段落檢查，以及產品 Python 與安裝器布局驗證。所有容量採十進位：1 GB＝1,000,000,000 bytes；容量不等於 RAM。

2026-10-19 補充：[T1 句內聲學切分實測](lyrics-t1-acoustic-segmentation-2026-10-19.md)依使用者釐清的顯示目標比較 A／B／C／D，找到較小的中日文歌唱音素候選及二套件環境。該輪以已知 T1 的詞塊起點為目標，與本文完整起訖任務不同；新的容量與選型須連同條件閱讀。

結論：保留 Qwen3 ForcedAligner 作為多語、已有正確歌詞的對齊草稿候選；中文 CTC 作為較省容量的字首定位候選。兩者均未達自動覆寫既有逐字歌詞的採用門檻。分離人聲確實能改善部分歌曲，但不能固定使用分離結果；活動模型、短句重切與原曲／人聲共識均不能替代內容與版本檢查。現在可先採用不增加模型的時間合法性、文字保留與重複句 occurrence 檢查。

## 1 證據分級與實驗範圍

使用者目前有逐字歌詞及模型段落紀錄，沒有人工校對真值。因此分為三種證據，數字不得混稱準確率。

| 證據               | 實際資料                                                  | 能回答的問題                                       |
| ------------------ | --------------------------------------------------------- | -------------------------------------------------- |
| 獨立逐字／音素標註 | MIR-1k-partial-align 中文、PJS 日文 sample 的人工音素標註 | 相對於獨立標註的時間誤差                           |
| 外部逐字參考       | 本機曲庫 T2，以及另外查得的韓文 T2                        | 與既有時間的一致性、可輸出邊界比例；不能當人工精度 |
| 獨立段落標註       | SongFormBench-CN 三首                                     | 段落邊界及角色評估                                 |

共測 32 個歌曲來源、57 個原曲時間窗口：中文 MIR 10 首、日文 PJS 1 首、本機／外部參考中文 6 首、日文 10 首、韓文 5 首。每窗口的 clean／mix／quick 是相同內容的消融，不能加算歌曲數。這些窗口共 2,311 個參考單位；不同語言單位不等同，不合併成多語總準確率。另有 24 個控制／破壞輸入及 12 個純伴奏窗口，負向輸入不計入精度分母。

中文獨立資料使用 [MIR-1k-partial-align 作者的人工字級標註](https://github.com/navi0105/LyricAlignment/tree/main/dataset_preprocessing)，不是本輪模型產生的標註。音訊取自固定 revision 的公開 MIR 鏡像，逐檔比對 LFS SHA-256。原始 stereo 是左伴奏、右人聲；mix 為兩聲道平均，clean 為右聲道，quick 為現有 KARA2 從 mix 重新分離的人聲。clean 是理想人聲上限，不能宣稱是分離器達成的效果。原始 16 kHz 資料升到 44.1 kHz 再送既有分離器，未增加原有頻寬。

中文每首固定取起點 0 及歌曲中點附近、最長 25 秒的窗口，只評完全落在窗口內的字。探索 6 首、12 窗口、515 字；確認 4 首、8 窗口、340 字。探索組其中一首兩窗口有重疊，且同首歌的字並非獨立樣本，不做字數級顯著性推論。

日文採 [PJS 官方 sample](https://sites.google.com/site/shinnosuketakamichi/research-topics/pjs_corpus) `pjs056.wav`，以[另行人工標註的音素時間](https://github.com/UtaUtaUtau/pjs-manual-labels)合成 21 個可比較詞塊。音素轉假名採固定映射；模型詞塊若切開不可分的 mora，合併參考詞塊，不按字數插時間。另加 MIR 伴奏作 0 dB RMS 合成混音。完整 PJS 下載受到 Drive quota 限制，未繞過；單一 sample 不能代表商業 J-pop。音訊與標註來源標示 CC BY-SA 4.0。

外部參考探索組為中文 569、日文 429、韓文 126 單位。確認組另外選未使用的日文 4 首／191 單位、韓文 4 首／120 單位。韓文新參考由產品既有公開歌詞 client 取得，不傳送音訊；只有完整 T2 才收錄。中文／日文／韓文既有 provider 資料的校對程度未知。參考中有重疊唱詞的案例保留並標記，沒有為提高成績排除。

確認組在結果產生前固定 Qwen 權重、0.6 秒句窗 padding、活動門檻、共識容差及方法檔 SHA；事後查核檔案未變。中文 CTC 的「未知字保持未對齊、其他字繼續跑」是確認結果後補做的公平基線，屬後續探索，不能宣稱事前註冊。

MIR 原始音訊的商用再分發條件未由本輪確認，不隨產品打包、不用於訓練。SongFormBench card 標示 CC BY 4.0；本輪使用發佈的 MP3，card 亦提供 vocoder 重建流程，不假設是原始母帶。資料集條件與待部署模型授權分開判斷。

| 中文 wav2vec2 XLSR-53 CTC          | `99ccb2737be22b8bb50dcfcc39ad4d567fb90cfd`                 | 1,276,342,318 B                   | Torch CPU，6 threads                  |
| Silero VAD TorchScript             | `1e261b036686cd0017d500ee96acd1c4ba572a9d`                 | 2,272,526 B                       | CPU，1 thread，posterior ≥ 0.5        |
| YAMNet ONNX                        | `f25b741c2f0bdc6d7e6db24b5fddda23347dbafd`                 | 模型 16,093,355 B，另有 class map | 既有 Node ONNX Runtime CPU，2 threads |

| 節拍／段落                         | 現有 Beat This! small0／受 gate 限制的 All-In-One Harmonix | 沿用既有 pack／研究環境           | 使用原有 worker                       |

[Qwen HF native](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B-hf)使用 Transformers 5.20.1 的本地原生實作，沒有下載執行任意遠端 Python。既有歌詞的單位可直接送官方 chat template，省去自行斷詞的日韓依賴；測試全程保留文字順序，不以新 ASR 改寫歌詞。[中文 CTC](https://huggingface.co/jonatasgrosman/wav2vec2-large-xlsr-53-chinese-zh-cn)為已知文字的 Viterbi 對齊，不是本輪自動聽寫。

評分以每個參考單位的開始／結束邊界為準。只有模型真的輸出對應文字邊界才有時間；不能把粗詞塊按字長切成細字。缺失、零長、越界、非單調、落在所屬句窗外的輸出列為未接受。開始誤差 ≤100 ms 的比例以全部參考單位為分母；中位誤差只對接受的時間計算，另列覆蓋，避免低覆蓋掩飾錯誤。起訖同時命中另行計算。

本輪在 Windows 11、約 64 GB 級 RAM、16 logical CPU 主機執行；有 RTX 5060 Ti 16 GB 但未使用 CUDA。Qwen 各批處理 RSS 約 4.40–5.05 GB；中文 CTC 原始批次約 2.71 GB。這是含載入器、評估與活動檢查的研究 process RSS，不是純權重或 VRAM。批次有並行運算，不把耗時當硬體性能排名或產品 SLA。

## 3 中文獨立標註：人聲分離改善，但起訖仍未過關

以下為 Qwen 原生文字單位。開始命中率分母包含缺失字。

| 階段／515 或 340 字 | 原混音：開始 ≤100 ms | quick 人聲：開始 ≤100 ms | 理想 clean 人聲：開始 ≤100 ms |
| ------------------- | -------------------- | ------------------------ | ----------------------------- |
| 探索 6 首           | 67.2%                | 73.8%                    | 88.9%                         |
| 新歌確認 4 首       | 47.6%                | 59.1%                    | 87.9%                         |

改善方向在新歌曲重現，確認組增加 11.5 個百分點。但確認組 quick 覆蓋僅 79.4%，字尾中位誤差 167.9 ms，起訖同時 ≤100 ms 只有 18.8%。clean 覆蓋 98.2%、字尾中位 39.8 ms、雙邊界命中 73.8%。這表示更乾淨的人聲有價值，也表示現有分離結果與理想人聲仍有顯著差距，不能直接推出「加對齊模型即可得到精準逐字」。

為公平比較 CTC，另跑不認識的字明確留空、其餘字繼續對齊的版本，所有字仍在分母。沒有自動繁簡轉換；中文原生詞彙外字仍是限制。最初「一個未知字就拒絕整個片段」會過度壓低 CTC，因此不以該結果淘汰模型。

| 新歌確認 340 字 | 覆蓋  | 開始 ≤100 ms | 結束中位誤差 | 起訖皆 ≤100 ms |
| --------------- | ----- | ------------ | ------------ | -------------- |
| Qwen 原混音     | 73.5% | 47.6%        | 203.7 ms     | 13.8%          |
| Qwen quick      | 79.4% | 59.1%        | 167.9 ms     | 18.8%          |
| Qwen 理想 clean | 98.2% | 87.9%        | 39.8 ms      | 73.8%          |
| CTC 原混音      | 99.1% | 77.1%        | 310.2 ms     | 0.6%           |
| CTC quick       | 99.1% | 81.5%        | 298.8 ms     | 0.6%           |
| CTC 理想 clean  | 99.1% | 88.8%        | 309.0 ms     | 0.6%           |

CTC 有明確的容量／字首定位優勢，但這個 spike-based 解碼的字尾通常太早，不能當唱字持續時間。直接拿下一字開始填字尾也不是實測字尾，不用此方法美化結果。若產品只需要字首 cue，可以保留中文 CTC 候選；若需要完整掃色與收尾，不能只看它較高的開始命中率。尚未測歌唱專用 CTC、繁簡詞彙適配或專門持續時間解碼，不把本基線缺點推廣到所有 CTC。

## 4 日韓與既有逐字參考：保留單位有收益，分離並非固定優勝

這一表為外部參考的一致性，不是獨立人工精度。「既有單位」只提供詞塊文字，沒有把逐字時間送進模型。括號為可接受邊界的覆蓋。

| 語言／階段         | 原混音原生斷詞 | quick 原生斷詞 | 原混音既有單位 | quick 既有單位 |
| ------------------ | -------------- | -------------- | -------------- | -------------- |
| 中文探索，569 單位 | 69.2%（91.0%） | 84.4%（96.1%） | 67.8%（91.0%） | 82.8%（96.0%） |
| 日文探索，429 單位 | 29.8%（60.8%） | 49.9%（69.2%） | 23.3%（68.8%） | 35.4%（83.0%） |
| 日文新歌，191 單位 | 20.4%（40.3%） | 28.3%（40.8%） | 36.1%（72.3%） | 49.2%（78.5%） |
| 韓文探索，126 單位 | 28.6%（66.7%） | 15.9%（52.4%） | 27.8%（65.9%） | 13.5%（53.2%） |
| 韓文新歌，120 單位 | 35.8%（60.8%） | 33.3%（52.5%） | 40.8%（74.2%） | 30.8%（65.8%） |

日文新歌既有單位明顯改善覆蓋與時間一致性，但探索組同方法較差，不能宣稱普遍提升。韓文兩組原混音整體均優於 quick，因此不可「只要有 vocal separation 就只用 guide」。分離、和聲、連音、拖音與參考文字單位不一致都可能影響結果；本輪不能對每個原因作因果歸屬。

日文獨立 PJS sample 的 Qwen 原生開始命中為 clean 95.2%、合成 mix 95.2%、quick 81.0%；仍是 21 詞、單一 sample 的結果，不能覆蓋上述日文商業歌曲的不確定性。韓文目前沒有獨立人工逐字真值，5 首的外部一致性只能支持繼續候選，無法通過韓文精度 gate。

短句窗使用既有 T1 起訖加前後各 0.6 秒，沒有偷用逐字時間。日文新歌 quick 既有單位開始一致性從 49.2% 降至 45.0%；韓文新歌 quick 僅 30.8%→31.7%，原混音維持 40.8%。因此不採固定短句重切作預設；已知句級位置可用來限制錯段與補救，應保留跨句上下文，再獨立驗證窗口策略。

general 只針對原生 quick 零長比例 ≥20% 的六個壞案例補跑，沒有按真值選案例。中文一例開始命中 40.5%→52.4%，韓文一例 16.7%→50.0%，另兩個韓文片段仍只有 8.3%、8.8%。這支持保留較高品質分離的補救入口，尚不足以依模型自我分數自動挑 winner，更不足以預設對所有歌多跑一次 general。

## 5 活動、重複、缺句與錯版本檢查

活動參考採逐字區間聯集，表示「有參考唱詞的區域」，不含所有呼吸、哼唱、和聲等完整人聲真值。活動召回只能如此解釋。字保留定義為該字真實區間至少 20% 被活動 mask 覆蓋，並非模型正確辨識了該字。

| 資料／輸入          | RMS 字保留 | Silero 字保留 | YAMNet ≥0.05 字保留 |
| ------------------- | ---------- | ------------- | ------------------- |
| 中文獨立確認／mix   | 100.0%     | 46.8%         | 7.1%                |
| 中文獨立確認／quick | 100.0%     | 62.1%         | 15.6%               |
| 日文外部確認／quick | 100.0%     | 74.3%         | 98.4%               |
| 韓文外部確認／mix   | 100.0%     | 3.3%          | 8.3%                |
| 韓文外部確認／quick | 100.0%     | 90.0%         | 94.2%               |

RMS 對純靜音有效，卻無法把伴奏與人聲分開。Silero 是 speech VAD，直接作唱歌硬 gate 會丟掉大量真字。YAMNet 有些分離後商業歌曲表現好，卻在獨立唱歌資料及未分離原曲明顯失效，因此同樣不採用作硬 gate，不能因只有 16 MB 就先放進預設包。

[YAMNet 這個 ONNX 匯出](https://huggingface.co/audiomagic/yamnet-onnx)包含 raw 16 kHz waveform frontend，非手工外掛 mel；本輪依模型 class map 實際索引讀 Singing（24）、Speech 等 vocal 類，沒有照錯誤示例假設類別索引。0.96 秒 receptive window、0.48 秒 hop 也不具逐字邊界解析度。門檻 0.05／0.1／0.2／0.5 均留存，沒有事後選出最好門檻作正式決策。

12 個獨立 MIR 左聲道純伴奏窗口，YAMNet 在 0.05 的假活動比例 0.82%；但低假陽性與極低唱歌召回同時存在，不能當良好分類器。Qwen 在這些沒有主唱的輸入上仍給出 55／515 個通過時間結構與 RMS 檢查的詞，證明強制對齊必須另外確認內容是否存在。

間隙檢查把 ≥1.2 秒無活動、離窗口邊緣 ≥0.8 秒的區域取中心，比較人工唱詞空檔。中文探索 quick 的 12 個參考空檔：RMS 找到 0 個候選；Silero 提出 21 個、±0.5 秒命中 8 個；YAMNet 提出 25 個、命中 2 個。中文確認 quick 只有 2 個參考空檔，Silero 提出 12 個、命中 1 個，YAMNet 18 個、命中 1 個。這些空檔頂多是呼吸／休止候選，不能直接作歌曲 verse／chorus 邊界。

破壞輸入採四個控制片段，各測純靜音、截斷一半、倒序單位、全文重複兩遍、換成另一片音訊。下表為每字檢查後仍被接受的數目，不把刻意錯誤的文字／時間拿來算對齊準確率。

| 輸入         | 要求單位 | 僅時間結構接受 | 加 RMS 接受 | 加 Silero 接受 | 加 YAMNet 接受 |
| ------------ | -------- | -------------- | ----------- | -------------- | -------------- |
| 正常控制     | 116      | 107            | 106         | 92             | 87             |
| 純靜音       | 116      | 6              | 0           | 0              | 0              |
| 截斷一半     | 116      | 58             | 57          | 47             | 44             |
| 倒序歌詞     | 116      | 76             | 62          | 47             | 58             |
| 全文重複兩遍 | 232      | 109            | 108         | 93             | 88             |
| 換成別首音訊 | 116      | 78             | 75          | 70             | 68             |

時間結構能抓缺失與不合法時間，RMS 能擋靜音，但仍接受大量錯序與錯歌單位。四個正常控制也沒有任一片達「全字皆通過」，所以把一個壞字提升成整首拒絕同樣不可行。需要逐區間保留未知狀態，並為錯版本／錯詞加獨立內容證據；本輪未用額外 ASR 驗證，不能宣稱已有完整解決方案。

30 份完整 T2 文件共 10,364 個 segment；28 份含至少四個正規化字元的重複句，共 258 組／686 次 occurrence。相同文字不能當時間快取 key 或跨副歌複製字時；必須以歌曲版本、行序、出現次數、來源時間窗識別。測試證明同文句仍分配不同單位索引，負向重複輸入亦保留，不自動去重。這是文字／序列品質檢查，不代表已判定每組都為副歌。

另測原曲／quick 都有合法時間、開始相差 ≤160 ms、結束相差 ≤240 ms 才保留並取均值的共識方法。中文獨立確認覆蓋降至 55.0%，保留者開始命中 82.4%，但全部字開始命中只有 45.3%，低於 quick 單跑 59.1%；日文／韓文確認既有單位的覆蓋僅 44.0%／26.7%。共識可標記「兩路一致」供檢查，無法變成整首高精度，更不能把拒絕字按長度補回去。

## 6 歌曲段落：取得獨立標註後的結果

使用 [SongFormBench-CN](https://huggingface.co/datasets/ASLP-lab/SongFormBench) 固定 revision `acd574ecbf666be535b0d051b71936f6ec9956ec`，推論前按 ID 排序取首三首 `BC_01bc5b`、`BC_032f29`、`BC_04e35a`。沒有與既有曲庫重合；只下載這三首，未下載整個 5 GB 級資料集。這次是獨立 expert 標註的評分，不是舊模型紀錄自評。

模型使用既有 gated All-In-One Harmonix worker，未新增 SongFormer 模型。按資料集指定把 pre-chorus 映成 verse、inst 映成 instrumental。評分同時保留原始段落，以及雙方均合併相鄰同角色後的角色轉換邊界；排除音訊頭尾 0.1 秒內邊界。邊界一對一匹配，避免一個真值被多個預測重複得分。

confidence 篩選只是已固定門檻的診斷，不把模型 confidence 當已校準正確機率。三首仍是小樣本，且沒有日韓獨立段落標註。角色粗分類有用，半秒級切段仍不可靠，不能依其邊界硬切逐字對齊音訊，更不能以 chorus 標籤自動覆蓋重複句的時間。

## 7 真正要下載與安裝多少

以目前產品 Python 3.14.7、Windows x64、Torch 2.11 CPU 為基礎解析候選 lock。現有 M1 的 16 個 artifact，其版本、bytes、SHA-256 在候選聯合環境完全相同，沒有另裝一套 CUDA。wheel、模型與 Python runtime 分開計量；FFmpeg 及既有 separation／Node runtime 不重複算進 Python 增量。

| 候選聯合環境                         | packages | 全部 wheels 下載 | 現行安裝器布局，未產生 pyc |
| ------------------------------------ | -------- | ---------------- | -------------------------- |
| 既有單位對齊，含 M1 共用依賴         | 41       | 162.16 MB        | 597.93 MB                  |
| 另加日韓自動斷詞                     | 52       | 235.21 MB        | 799.63 MB                  |

容量不是只看 pip metadata。逐 wheel 計算 ZIP 解開檔案、保留 `.data` 並按產品 installer 複製 purelib／platlib；41 套件另外實際解包，布局共 597,930,408 B，與計算相同。接著真的呼叫產品 `defaultProbeEnvironment`，驗證全部版本及 beat_this／numpy／torch／torchaudio／transformers imports，成功後含新增 pyc 為 621,925,815 B。52／67 套件列的是 raw installer 布局，不宣稱已完成相同產品 probe 後的容量實量。

既有單位版本以標準庫讀 PCM16、既有 FFmpeg 解碼，避開額外音訊 IO／特徵套件。中文、日文、韓文、英文四個 probe 在 pip target 與真正 installer 布局輸出逐詞完全相同；既有 Beat This! worker 在現用環境與此候選環境的同一音訊結果完全相同。這支持共用環境的可行性，不等於已經整合產品安裝、IPC、取消／重啟與 packaging。

下表安裝總量包含 Python runtime 24,647,944 B、既有 small0 模型目錄 8,451,978 B、上述實際 probe 後的 41 套件及選定對齊模型。既有 baseline 約 0.563 GB。需完成聯合環境遷移並清除舊環境後，才有表中的共用總量。

這些下載數包含整份 41-package wheels；目前安裝器不同 capability lock 不會實體共用既有 16-package 檔案，亦無可依賴的全域 wheel cache，所以不能只顯示新增套件的理論差額。模型目錄已存在且 integrity 通過時可重用。全新機器還要加 Python runtime archive 約 12.67 MB 與 small0 必要檔案約 8.45 MB；表中並非首次安裝總網路量。

若從既有單位改成日韓自行斷詞，raw 環境多約 201.70 MB，理論 wheels 差 73.05 MB；但現行新 lock 流程要下載整份 235.21 MB、暫存完整新環境，舊 lock 需待新 probe 成功才可回收。Qwen＋52-package raw 總量約 2.680 GB，尚未加其 product probe pyc；不把它當精準的完成安裝量。已有逐字單位時，這項額外成本沒有穩定的品質收益，不放進優先環境。

Silero 2.27 MB、YAMNet 約 16.11 MB 本身都很小，但本輪召回不足，因此不納入預設；YAMNet 可走現有 Node ONNX 路徑，無需為它加 TensorFlow。KARA2／HQ4 沿用既有 separation 環境，模型本身為數十 MB 級，不能誤算成另一組 GB Python 包。

容量數是檔案 logical bytes，未含 NTFS allocation、下載快取、暫存 WAV、模型執行 RAM、安裝時新舊並存及 archive，不能拿完成安裝量當磁碟空間檢查上限。現有下載器把整個檔案留在 Buffer 並 concat，GB 模型正式支援前需要 streaming、校驗、暫存與復原設計；本輪直接研究下載成功不代表產品 downloader 已可承受。

## 8 模型與環境採用決定

近期產品順序建議如下；這是研究選型，不是已改變 feature registry 的產品狀態。

1. 沿用已有歌詞與分離結果，先加入沒有額外模型的時間／文字／重複 occurrence 品質契約；任何失敗保持未知，不補假時間。已有 T2 保留來源與版本，新的模型輸出另作候選。
2. 如需完整多語時間草稿，優先 Qwen＋41-package CPU 環境；已有 segment 文字就直接用，不先下載日韓斷詞與 librosa。原曲與 guide 都有價值，暫不依未校準自我分數自動選擇，也不強制雙跑所有歌。
3. 若產品明確只做中文開始 cue，可選較省約 0.571 GB 權重的中文 CTC；不能包裝成同等完整起訖能力。只為中文測試就同裝兩個大模型沒有必要。
4. 暫緩 Silero／YAMNet 硬 gate、固定短句裁切、節拍吸附、共識後自動補字，以及受非商用限制的段落模型。保留警示／研究輸出，不直接變更使用者時間。
5. 不追加大型 ASR、CUDA、SongFormer 或更多 separation pack 作預設。若要解決錯版本／缺句，下一輪只對獨立內容驗證方法作控制實驗，證明能攔錯且不拒絕正常歌曲，再決定是否值得另一筆 GB 下載。

CPU 41-package 方案已在現有產品 runtime 實跑，不要求使用者先安裝 GPU 環境。單 worker 需要約 5 GB 級 process working set，加上 Electron／OBS／系統，16 GB RAM 可作初步工程配置目標，但本輪沒有在 8／16 GB 機器驗證，不承諾該級延遲或 OOM 行為。32／64 GB 可容納較多工作，仍應串列模型生命週期；本輪只證明目前主機上的 CPU 可行，沒有證明 CUDA 會提高精度。

正式自動採用仍缺三項證據：日韓多首獨立人工逐字真值、全曲跨段／重複句／混合語言評估、以及低錯誤接受率的內容／版本驗證。中文現有 quick 的雙邊界命中也明顯不足。因此現在能決定「最先提供哪個可選草稿環境」，不能宣稱已有正式全自動精準 T2。
