日期：2026-10-19。成效與使用／分發條件分開比較。此次沒有新增模型下載、產品入口、activation、gate 放寬或 commit。[匿名量測與收據](data/lyrics-root-causes-2026-10-19.json)保留分母與來源身分。

## 可立即決策的結果

| 問題                 | 已定位原因                                                                                     | 低成本實測與決定                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| small 擋掉正常中文句 | 繁體歌詞對簡體 ASR；T1 起點比 ASR 句首晚約 1.29 秒，固定 ±500ms 取詞漏掉句首，並混入下一句英文 | 僅比較時用既有 OpenCC，正常詞塊輸出 24→25 句；三個合成錯配仍全攔。優先保留此研究修法，不改原文或時間  |
| Qwen 日文缺界        | 模型詞粒度與顯示斷詞不同；部分多字詞只提供整詞起點，另外有起點落在 T1 外而被丟棄               | 模型詞內等距補切：可評缺界 6→2，但 ≤100ms 仍 12／35。只提高可顯示切點，不宣稱更準                     |
| 日文時間長尾         | 原始模型詞起點已偏移，重複片語、零長／過長 span 與屈折詞尾另有問題，不只是 parser 缺界         | 不能靠補切修正整個詞的錯起點；直接以均分壓住模型分歧，反而損失準確點並重新出現 >1s 長尾。先提示與人審 |

small 的該句相容率原為 1／6，繁簡統一後為 2／6，僅因此跨過原本 0.2 的矛盾門檻；不是已完整認出那句。ASR 中仍有實際異字，下一句的英文也仍在取詞區間。正常輸出恢復不等於已經人工確認正確。

額外測試「±1.5 秒鄰近句首，至少四字且 ≥0.8 相容才救援」，本輪沒有比單純繁簡處理多救回案例，因此不增加這條複雜度。救援只將判定退回 unknown，沒有重設 Qwen 時間。它可能受鄰句／重複句干擾，不是正確性認證。

## 原始輸出診斷與消融

對新四首正常片段重新執行 Qwen，保存 worker 原始 text／start／end span。四案均逐一重現先前的顯示 chunks；再由原 exact mapper 重建確認，不只信任紀錄中的布林。輸入、參考、音訊、canonical、模型、capture results、窗口與 wrapper code 均綁定。原始 span 只留本機，不公開歌曲文字。

日文第一首可評 19 點，Qwen 輸出 13 點；六個缺界都在日文句，英文四句在這個可評分母內是 0 點。不能把 8→2 個準確點的退步全推給「英文被拒」。六個缺界中可見整詞沒有內部起點，以及模型起點在行外／不單調而被既有 chunker 拒絕的兩種機制。模型原始長尾包括同一句兩個起點比 provider 早 905／867ms、另一句晚 677ms；新第二首有屈折詞尾早 643ms。這些仍需獨立聽查確認 provider 參考。

原始模型亦出現零長 span、約 3.36 秒的多字 span，以及句首在 T1 前約 1.3 秒的情形。這能證明輸出形狀，不能單憑它判斷真正唱詞起音。正式 T1 第一錨點與 T2 優先保持原樣。

| 正常新歌，固定 35 個可評內部切點 | ≤100ms | 缺界 | >500ms | >1000ms | 判讀                                                 |
| -------------------------------- | ------ | ---- | ------ | ------- | ---------------------------------------------------- |
| 現有均分                         | 15     | 0    | 2      | 1       | 固定基線                                             |
| Qwen 原始映射                    | 12     | 6    | 5      | 0       | 實際量到 29 點                                       |
| 模型 span 內等距補切             | 12     | 2    | 5      | 0       | 多補四個切點，沒有增加準確點；是插值，不是量到新音節 |
| 補切後，分歧 >500ms 整句退回均分 | 10     | 1    | 3      | 1       | 過度回退也會傷到 Qwen 原本改善的長音句；不採自動硬套 |

另補兩首日文實推論對照：第一首從可處理日文起點前2秒裁去 11.463 秒開頭，第二首裁 0 秒作控制；仍用原完整 canonical 與35點評分，不移除英文句或缺界來美化分母。結果為 ≤100ms 13／35、缺界9、>500ms 3、>1000ms 0；第二首逐塊重現原結果。可見保留未轉錄英文音訊值得注意，但裁去它沒有穩定解決退步，反而多缺三點，不採為通用修法。裁切 offset 只加回一次，模型身分、wrapper／validator hash 及來源綁定，並通過原文／回退／程序清理驗證。

前輪報告把這 35 點描述為含 T1 第一錨點，該文字有誤；凍結的 `scoreCuts` 一直只用 `cuts.slice(1,-1)`，因此數字未變，已更正說明。

內容修法另重播新 16 案、舊 22 主案與 7 壓力案。新案正常 24→25、三個有效合成錯配保持 0 輸出，漏詞仍沒有解決。舊主案的 small 內容檢查原輸出 283 句，繁簡處理後 285 句；可評恢復三點，但 ≤100ms 不變，>1000ms 27→28。這說明「內容判斷救回」與「詞界時間準」仍是兩件事。七個壓力案輸出數不變，錯歌仍有一行被接受，不能聲稱已堵住所有錯歌。

完全改為警示雖可保留正常句，會重新放過新三個合成錯配，舊錯音訊也由一行增加為三行；此消融只顯示取捨，不當成改善。這些是對已看過失敗案例設計的探索，未視為 held-out 校準或人工誤接受／誤拒率。

## 開源專案是否可以用 NC 模型

可以有合法的非商用使用路徑；前輪「排除一般產品選配」不是全面禁用所有非商用研究／開源專案。技術成效表保留候選，使用和分發條件另判斷。

| 情境                                 | 判斷                                                                                                                                                                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 符合非商用用途的研究或自用           | CC BY-NC／NC-SA 並非禁止；仍依指定權重條款與其他必要權利。 [CC BY-NC](https://creativecommons.org/licenses/by-nc/4.0/)                                                                                                                                                     |
| 非商用分享原權重／修改權重           | NC 不是禁止分享。保留來源、署名、授權及修改資訊；若分享構成改作的 NC-SA 材料，依其 SA 條件。 [NC-SA 法律條文 §2–3](https://creativecommons.org/licenses/by-nc-sa/4.0/legalcode.en)                                                                                         |
| 程式碼開源，權重另有 NC 條款         | 可分別標示程式與模型條款，不能把權重重新宣稱 MIT 或無用途限制；僅同放 repository 不足以判定整個 app 必須換授權，是否改作須另看結合方式。 [CC 結合／改作 FAQ](https://creativecommons.org/faq/#can-i-combine-material-under-different-creative-commons-licenses-in-my-work) |
| 免費 app、使用者自行下載，或營利直播 | 這些不會自行解除 NC。是否主要為商業利益／金錢報酬，依實際用途判斷；營利直播不能一概列為已獲准的 NC 用途。 [CC NC 官方說明](https://creativecommons.org/faq/#does-my-use-violate-the-noncommercial-clause-of-the-licenses)                                                  |
| 特定權重授權未明／標示衝突           | 不能用「專案開源」填補未知許可；也不能把未知直接寫成確定禁止。維持證據待確認。                                                                                                                                                                                             |

工程上可考慮「開源程式核心＋條款獨立的非商用模型選配」；這是設計建議，不是此次已開放下載。須清楚標出哪些部分受 NC 限制，不能宣稱整套所有資產都符合無用途限制的開源定義；[OSI 定義](https://opensource.org/osd)要求不得限制商業使用。模型條款、錄音／歌詞來源、輸出使用情境仍分開。

因此本輪只修正研究與授權解讀，不自動放寬正式 gate。模型是否值得採用，先看相同資料的成效與故障；可提供在哪種使用範圍，再依指定權重條款決定。
