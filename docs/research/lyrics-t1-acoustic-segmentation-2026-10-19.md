# T1 句內聲學切分實測與模型環境評估

研究收斂與實作邊界見[實作評估入口](lyrics-acoustic-segmentation-implementation-assessment-2026-10-19.md)。本文保留本輪實驗證據，並非產品已採用狀態。

日期：2026-10-19。接續[中日韓完整起訖對齊實測](lyrics-alignment-cjk-evaluation-2026-10-18.md)，本輪改以「已有正確整句文字及 T1，改善詞塊切換與高亮起點」為目標，依序執行 A 現行估算、B 人聲起音與序列約束、C 節拍弱約束、D 歌唱專用音素模型。時間與容量為實測；未改產品 registry、activation 或使用者歌詞。

結果支持優先把 HubertFA 類歌唱音素對齊列為中日文 T1 輔助切分候選。中文確認組的句內字首 ≤100 ms，現行 T1 為 28.3%、DSP 為 50.7%、HubertFA 為 78.9%；改成文字詞塊切點則為 28.4%→81.4%。重用現有日文讀音工具後，新增環境只需 NumPy 與 pypinyin，含模型新增安裝約 0.466 GB，無需新增 Torch／CUDA。節拍及低成本活動門檻尚無穩定收益；韓文未被這份 checkpoint 覆蓋，休止停掃與錯詞驗證仍須另外處理。

## 1 資料與評分邊界

沿用前輪固定音訊及參考，共 32 個歌曲來源、47 個原曲窗口；加入 quick／理想 clean 消融後為 105 個音訊窗口、614 個句級案例。相同內容的消融不是獨立歌曲。614 案例對應 277 個句級外框，其中 217 個為 provider T1，60 個為獨立資料上合成的粗時間外框。

中文獨立資料是 MIR-1k-partial-align 的人工字時，取每首第一個窗口，避免上一輪部分窗口重疊。探索 6 首、35 個粗句、235 個可評句內字首；確認 4 首、22 個粗句、152 個句內字首。各粗句按文字順序分為八個參考單位，尾段不足四個則合併；只把首單位開始及末單位結束提供給演算法，內部時間只供評分。這是 oracle 外框條件，不是額外找到 22 句人工 T1，也未證明能從無時間全文找到句子。

日文獨立 PJS 單一 sample 分為三個粗句，共 18 個可評內部起點。它不能代表多首 J-pop。真實歌詞資料則保留既有 T1 與逐字外部參考；日文確認為四首／164 個句內參考起點，韓文確認為四首／96 個句內參考起點。外部參考的人工校對程度未知，因此只稱一致性。

評分排除已給定的句首；句尾也不作推論成果。所有缺失、不可細分及超出 T1 的起點仍留在各自指標分母。不是只評模型願意輸出的字。字首誤差與覆蓋分開報告，另計提前在前一字參考結束前 100 ms 跳字，以及落入 ≥250 ms 參考休止內的切點。

B 只在六首探索中文的 quick 音訊選參數，C 亦只用該組選權重；設定凍結後才計確認組新方法結果。確認音訊在前輪 Qwen 研究中已使用，這不是從未被研究者看過的盲測。模型訓練資料是否與評估歌目完全不重合，本輪亦未確認，不作訓練外泛化或整體中日韓準確率承諾。

## 2 A 現行產品 T1 基線

A 直接擷取並執行目前 `shared/presentation/state.mjs` 的 `estimatedPresentationSegments`，使用正式 `estimatedLyricsTextUnits`，保存函式 SHA。沒有另寫一個較弱的均分器代替產品基線。現有方法按可見文字權重分配 T1 句長，不分析音訊。

比較所有方法時，文字、句級外框、來源窗口及可評參考相同。韓文現行文字單位較部分外部 T2 粗，確認組只有 83.3% 參考起點有可表示邊界；缺失仍留在分母，不插值補字。

## 3 B 人聲起音與單調長度約束

B 在 16 kHz PCM 上計算 40 ms 頻譜窗口、10 ms hop，結合正頻譜通量、能量起音及頻譜形狀變化。主要頻帶為 250–6,000 Hz；候選包含聲學局部峰與原 T1 估算點。動態規劃一次選擇整組邊界，維持順序與最小間距，以文字權重長度及估算位置作弱先驗。

探索組比較位置先驗 0.1／0.3／1.0 與長度先驗 0.05／0.15／0.4，依全部句內起點的 ≤200 ms、≤100 ms、median 順序選型，結果為 0.1／0.05。純靜音只回傳既有估計、沒有聲學可信邊界；但一般峰強度經局部正規化後不是正確機率。

| 確認組與輸入         | A ≤100 ms | B ≤100 ms | A median | B median |
| -------------------- | --------- | --------- | -------- | -------- |
| 中文獨立／原混音     | 28.3%     | 46.1%     | 228 ms   | 132 ms   |
| 中文獨立／quick 人聲 | 28.3%     | 50.7%     | 228 ms   | 95 ms    |
| 中文獨立／理想 clean | 28.3%     | 59.2%     | 228 ms   | 74 ms    |
| 日文外部／quick      | 42.1%     | 40.2%     | 122 ms   | 137 ms   |
| 韓文外部／quick      | 18.8%     | 22.9%     | 233 ms   | 254 ms   |

中文確認組有改善，但尾端錯誤仍大：quick 的 P95 為 A 975 ms、B 1,192 ms。日文沒有收益，韓文 ≤200 ms 一致性從 37.5% 降到 34.4%。不能以中文 median 改善宣稱多語普遍改善。

在峰強度 ≥0.35 才保留內部切點的合併版本中，中文確認 quick 幾乎所有切點都通過，並未有效分辨可靠與不可靠邊界。純伴奏 12 窗口的 503 個要求內部切點全部被標記為有聲學證據；錯歌、倒序及截斷也會留下大量候選。因此 B 可作顯示估計基線，尚不適合自動決定哪些字可拆開。

## 4 C 把拍點放進解碼

C 使用既有 Beat This! small0 worker 對 47 個原曲窗口實際產生拍點，採 confidence ≥0.1 的相鄰拍點建立四分之一拍格線。接近格線的聲學候選可獲得小幅加分；沒有聲學活動不能因有拍點就變成可信邊界。這是候選路徑的聯合選擇，與前輪「對齊完才移到最近拍點」不同。

開發組比較權重 0／0.05／0.15／0.3，選出 0，因此正式選型的 C 等同 B。另保留非零 0.15 的消融：中文確認 quick 的 ≤100 ms 為 44.7%，低於 B 50.7%；median 由 95 ms 變為 141 ms。不能因加入音樂訊號就假定更準。

理想 clean 上，固定 0.15 的 C 為 63.8%，高於 B 59.2%，但在可取得的 quick 上未重現。這支持繼續研究聲學品質與節奏權重的關係，尚不支持預設開啟。此次沒有獨立鼓 stem 或拍點人工真值，也沒有測 swing／三連音的自適應格線，不能把結果推廣為所有節奏方法無效。

## 5 D 歌唱專用音素對齊

選擇 [HubertFA v0.0.7 官方 release](https://github.com/wolfgitpr/HubertFA/releases/tag/v0.0.7) 的 `1218_hfa_model_new_dict.zip`，原始碼固定 `521281fe52dcedb8f970ca200dc4f00fc2869b08`。官方發佈說明為普通話與日文歌唱；本輪不把字典內有其他語言符號誤認為相應語言已驗證。韓文不在此次權重範圍。

ONNX frontend 使用現有 Node ONNX Runtime CPU，每窗口輸入完整 44.1 kHz waveform。再於 T1 外框前後各 0.35 秒範圍裁取聲學 logits，使用官方音素／邊界解碼。這保留編碼器的窗口上下文，不是把每句短音訊獨立送入模型；文字轉發音只讀 T1 文字，不讀句內真值。

實際推論 65 個音訊窗口、358 個句級案例；348 個成功解碼，10 個中英混合／數字輸入因讀音詞彙不支援而保留未知，仍計入評分。沒有讓上游字典靜默刪掉不認識的字。保留 SP 的原始解碼，不啟用會修補空隙或創造極短時長的 exporter 後處理。

日文先以 pykakasi 試跑，再測重用產品已有的 kuromoji 0.1.2 與 wanakana 5.3.1。後者不新增 GPL 授權讀音套件，也不增加日文字典下載。讀音選擇基於現有依賴，沒有按真值調模型參數；其成果屬本輪後續工程比較。下表 D 採這個現有讀音版本。

| 確認組／quick | 可評內部起點 | A ≤100 ms | B ≤100 ms | C 固定 0.15 | D ≤100 ms | D 覆蓋 | D median |
| ------------- | ------------ | --------- | --------- | ----------- | --------- | ------ | -------- |
| 中文獨立標註  | 152          | 28.3%     | 50.7%     | 44.7%       | 78.9%     | 99.3%  | 46 ms    |
| 日文外部參考  | 164          | 42.1%     | 40.2%     | 39.6%       | 70.7%     | 81.1%  | 26 ms    |

中文 D 原混音為 76.3%、quick 為 78.9%，差距僅 2.6 個百分點；日文外部原曲為 68.3%、quick 為 70.7%。已有 guide 可重用，尚無理由為此強制所有歌曲重新分離。中文 D 理想 clean 為 90.1%；日文獨立單一 sample 的 quick 在 18 個內部起點上為 94.4%，仍不能外推到日文整體。

中文確認 quick 的「在前一字參考結束前至少 100 ms 就切換」比例為 A 22.4%、B 18.4%、D 4.6%。但落入參考休止內的切點為 A 17、B 11、D 14，說明起點整體改善並不代表休止問題已一併解決。

這些數字不能與前輪 Qwen 的 340 字結果直接作模型排名：本輪只取每首第一窗口、排除已知句首，且 D 明確利用了 T1 外框。結論是更適合此 T1 任務的候選出現了，不是已證明 HubertFA 在所有條件勝過多語 Qwen。

## 6 直接評估顯示詞塊

先以 `Intl.Segmenter` word 模式從文字決定詞塊，完全不看音訊或參考時間。再映射 A 或 D 真正存在的起點；D 沒有該邊界就把詞塊合到前組，不按字數補出時間。句首沿用 T1 錨點，保持原文字與出現順序。

| 確認組／quick | 要求詞塊內部切點 | 有參考可評 | A ≤100 ms | D ≤100 ms | D 在可評點的覆蓋 |
| ------------- | ---------------- | ---------- | --------- | --------- | ---------------- |
| 中文獨立標註  | 102              | 102        | 28.4%     | 81.4%     | 99.0%            |
| 日文外部參考  | 148              | 108        | 40.7%     | 78.7%     | 92.6%            |

中文保留 101／102 個要求切點。日文全部要求切點保留 134／148，其中 40 個切點沒有相應外部參考邊界，不能替其估一個真值；表中 78.7% 的分母明確是 108 個可評切點。這與上節逐參考單位的 164 起點為不同評估任務，不能交替挑選較高數字。

這條路線符合「T1 提升顯示」：先提供有證據的詞塊起點，以切換／維持高亮呈現；連續掃色的字尾需要另外處理。此輪驗證的是時間與資料投影，尚未做可見 Electron／OBS 的主觀觀感驗收，不稱已完成 UI 效果改善。

## 7 休止 錯詞與外框偏移

D 的確認 quick 外框整體提早／延後 0.2 秒，中文內部起點 ≤100 ms 為 79.6%／78.3%，原為 78.9%；日文外部為 68.3%／68.3%，同次未偏移為 70.1%。這項日文偏移診斷使用初始 pykakasi adapter，尚未用最終 kuromoji adapter 重跑；不能拿上節最終版本的 70.7% 當同次基線。這支持測試條件內對小幅 T1 誤差的容忍，但沒有驗證整句定位錯段、重複副歌錯配或句首顯示；句首仍是給定錨點。

低成本 RMS 活動 mask 的休止 hold 診斷，中文確認 quick 幾乎沒有攔到參考休止；clean 理想人聲則可攔到約 50.5%。直接把 D 的原始 SP 類 posterior 當活動機率亦無效，確認組沒有攔到休止。因此此次沒有得到可採用的「遇到休止就停止掃色」方案。

D 另測三個控制片段各自的靜音、截斷、倒序、重複兩遍、錯音訊，加上十二個純伴奏窗口；共 30 個案例。日韓中的韓文不以不支援語言強行測 D。負向輸入不作準確率評分。

| D 輸入       | 案例 | 要求發音詞單位 | 仍輸出合法時間單位 |
| ------------ | ---- | -------------- | ------------------ |
| 正常控制     | 3    | 108            | 108                |
| 純靜音       | 3    | 108            | 108                |
| 截斷一半     | 3    | 108            | 108                |
| 倒序         | 3    | 108            | 108                |
| 全文重複兩遍 | 3    | 216            | 216                |
| 錯音訊       | 3    | 108            | 108                |
| 純伴奏       | 12   | 515            | 515                |

這是強制對齊的關鍵限制。三個正常控制的 confidence 約 0.501／0.443／0.537，對應靜音反而約 0.613／0.538／0.611；不能用較高 confidence 當內容吻合。原始 SP posterior 的 gate 亦全部放行，不具攔錯能力。實際流程至少要先拒絕全靜音，且「原歌詞與版本已確認」必須是輸入條件；此輪沒有解決錯詞／錯版本驗證。

## 8 漸進環境與容量

HubertFA 的模型 archive 為 256,589,553 B，GitHub release digest 比對成功。解開後完整模型目錄為 418,636,089 B，其中 ONNX 415,220,874 B。這是下載壓縮量與安裝量的差別，不能只展示 257 MB 當完整功能容量。

最初六套件研究環境為 NumPy、pypinyin、pykakasi、jaconv、Deprecated、wrapt，實際 product probe 後為 58,275,325 B。pykakasi metadata 標示 GPL-3.0-or-later；因此進一步驗證沿用現有 Node kuromoji／wanakana，讓新增 Python 環境只留下兩套件。

下表只計 Audio Python 與對齊模型選配，不包含 app 本體、既有 FFmpeg／分離包、音訊快取、NTFS allocation 或安裝暫存。研究 zip 的 SHA-256 為 `48bd6dbcc293e47cc6cbcc556baf575e3d91d61d0ac88ddeccd6098f8f346fa2`。

| 最終候選環境                | 實量                                                           |
| --------------------------- | -------------------------------------------------------------- |
| Python／平台                | 現有 CPython 3.14.7，Windows x64                               |
| 新環境套件                  | NumPy 2.5.2、pypinyin 0.55.0                                   |
| 二套件 wheels 下載          | 13,437,830 B                                                   |
| 現行 installer 原始布局     | 45,252,986 B                                                   |

兩套件環境實際用 wheel ZIP 解包、照現行 installer 保留並展開 `.data`；呼叫產品 `defaultProbeEnvironment` 驗證 imports 及版本。產品 Python 在這個環境重算 358 個案例，與原研究環境的時間輸出及失敗狀態完全一致；沒有載入 Torch、Python ONNX Runtime 或 pykakasi。模型推論在已有的 Node ONNX Runtime 完成。

研究本次下載 zip＋二套件為約 0.270 GB。但目前 model artifact 流程並未登記此模型或這個 archive 的展開契約；若維持現有逐檔發佈方式，按完整解包檔＋wheels 的下載預算約 0.432 GB，仍需可分發的 artifact hosting。0.270 GB 不能直接當目前 Settings 已能提供的下載量。

原始碼 Apache-2.0、pypinyin MIT、NumPy 與既有 Node 依賴有各自授權清單；本輪未把 GitHub 上可下載 checkpoint 視為商用權重 grant 已通過。模型 archive 也沒有完整訓練資料清單／獨立 weight license 證據。正式提供前須補模型來源與授權紀錄、環境 id／lock、Node worker、feature gate、取消復原與 packaging；本輪沒有啟用或宣告正式可用。

CPU 四 threads 的 65 窗口 frontend 推論合計約 96.7 秒；每窗口後取樣 Node RSS 最大約 1.445 GB，未作連續峰值監測。不是端到端等待 SLA，也沒有測 8／16 GB 裝置或 CUDA。它證明本機 CPU 有可行候選，不代表所有硬體已有相同性能。

## 9 採用方向與驗證結果

對這個 T1 顯示任務，中日文優先進入 HubertFA＋現有讀音工具的詞塊起點原型；先保留 T1 身分與未知邊界，採起點切換／維持高亮，另做可見播放驗收。可以用原曲起跑，已有 guide 再重用，不預設重跑分離。韓文保留現行 T1，另找真正支援韓文且可測的歌唱模型；不以中日文 checkpoint 充數。

B 不增加大型權重，中文有研究價值，但一般化與可靠切點判斷不足；C 目前不預設開啟。Qwen 保留多語完整起訖候選身分，不因新 T1 任務結果直接卸除或自動替換。沒有理由為此先載入 CUDA、大型 ASR 或兩個大對齊模型。
