# 歡唱受眾、選曲榜單與有限雲端：決策研究

日期：2026-10-26（Asia/Taipei）。Owner 提出從直播／翻唱延伸至一般 KTV 使用者，並研究播放統計、歌曲排行與有限雲端資料服務。本文件整理建議與進入條件；尚未接受為實作範圍、沒有新增服務或資料上傳。現行承諾仍見 [PRODUCT](../../../PRODUCT.md) 與 [spec](../../spec.md)。

## 1. 建議定位與受眾

建議研究的定位是「以本機曲庫為核心的 Windows 歡唱與練習工具，並支援歌唱演出及 OBS 輸出」。這是候選表述，沒有直接取代目前的正式定位。

| 使用者／情境     | 可共用的核心                                       | 需要先驗證                                                                          |
| ---------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 個人居家歡唱     | 本機匯入、歌單、待唱安排、歌詞、伴奏／導唱與變調。 | 自備素材到開始唱的準備成本；不連 OBS、不啟用外部服務也能完成主要任務。              |
| 翻唱與練習者     | 變調／變速、歌詞、逐曲設定、A–B 與對時候選。       | 保存／套用是否可靠、重練是否省步驟；Mic 回饋的實際價值另驗。                        |
| 朋友聚會操作者   | 同一台 Windows 主機、待唱安排與既有手機方向。      | 重複點同曲、換唱交接、遙控配對／撤銷；多人登入、遠端共編與多支 Mic 混音不隨之納入。 |
| 歌回／直播操作者 | 上述核心加上 Output、BGM 與 OBS 整合。             | 延續真實擷取、視覺與長時間演出驗收，保留原使用者的可靠操作。                        |

擴大的共同任務是準備歌曲、選曲、開唱與練習。榜單主要解決「下一首唱什麼」，不能取代可播放素材、可讀歌詞及音訊準備。「任何想 KTV 的人」仍是待驗證的願景；目前 Windows 與自備媒體門檻未消失，不能推論手機瀏覽器或開箱即有完整曲庫。

先以不同情境測同一條工作流，不先增加身分版本、互不相通的播放模式或新的導覽殼層。引導仍等待既有視覺前置；這份研究不提前啟動其 UI 實作。

## 2. 榜單與統計的四種不同目的

| 類型                   | 使用者價值                           | 資料與依賴                                           | 建議分類                                 |
| ---------------------- | ------------------------------------ | ---------------------------------------------------- | ---------------------------------------- |
| 個人常播／練習統計     | 找回常唱曲、挑選較少練的歌曲。       | 先用本機資料；播放與實際演唱要分開命名。             | 優先定義最小範圍。                       |
| 編輯選曲／外部公開榜單 | 幫使用者挑選主題、熱門或適合的歌曲。 | 人工整理或有明確可用範圍的一手來源；須標來源與日期。 | 可先做只讀資料樣本，無須先收集使用紀錄。 |
| Utawakui 社群熱門歌曲  | 了解自願參與者近期播放／演唱的歌曲。 | 選擇性資料貢獻、共同歌曲識別、去重、聚合與樣本限制。 | 有限雲端研究候選。                       |
| 歌唱分數／歌手排名     | 比較演唱表現。                       | Mic、參考旋律、對齊、設備差異與評分公平性。          | 獨立低優先候選，不隨歌曲熱度榜納入。     |

本輪重新區分歌曲熱門榜與演唱成績競賽：既有 Mic 計畫仍不投入分數排行，歌曲探索／播放統計則新增為研究候選，不沿用早前一概排除雲端排行榜的判斷。舊日期報告保留當時決策；此分類仍不是採用任何榜單的承諾。

## 3. 既有資料能做什麼

現有[播放紀錄契約](../../contracts/playback-history-and-resume.md)及 `electron/lib/playbackPersistence.js`／`src/utils/playbackHistoryQualification.js` 是核對入口：

- `playback-usage.json` 已有本機 `playCount` 與 `lastPlayedAt`；不需要先上雲才能研究累計播放排序。
- qualified playback 是實際進度累計 10 秒或短曲自然結束；它證明播放行為，不證明使用者開口演唱、完成一首歌或練習有效。
- 最近播放按曲去重、保留最近項目，usage 是累計值；不能由此重建歷史每週榜、每次演唱或每天練習時數。缺失期間不得補成零或推算成事實。
- [播放安排](../../contracts/performance-session-preparation.md)另有 occurrence 與明確進度。完成／略過／中止的語意不能直接與一般播放次數合併。
- BGM 與 A–B 練習循環應有排除／去重規則；不應逐輪放大社群人氣。Manual 外部音訊沒有可驗證的共用歌曲識別時，不強行歸榜。

第一份小規格應先回答「要顯示累計播放、近期播放，還是場次完成次數」。若確需時間窗統計，再提有界的本機彙總／事件保存與遷移方案，沿用現有 owner，不為雲端先建立另一套播放紀錄權威。

## 4. 有限雲端的最小邊界

Local-first 的產品條件是：沒有網路、帳號或雲端服務時，匯入、曲庫、播放、歌詞與本機統計仍能使用。可選資料服務可以研究，但不能悄悄變成啟動或核心播放的前置條件。

候選資料流分為兩條，應獨立設計：

1. 讀取選曲資訊：下載有版本／日期的歌曲清單與聚合榜單，本機快取；不以加入資料貢獻為代價，也不暗中附帶個人播放紀錄。
2. 自願貢獻統計：獨立明示同意後，才提交用途明確、限量的彙總。預設不送、不回補同意前歷史；關閉、待送資料清除及已送資料處理能力需先定義。

第一階段候選只需要歌曲參照、時間桶與有界計數；對未知本機歌曲可直接排除。不要上傳音訊、Mic 錄音、歌詞全文、封面檔、檔案路徑、完整曲庫清單或逐秒時間線。當前 feature gates 與錯誤回報同意不授權這些新用途。

讀榜可先用可快取的靜態資料驗證價值。之後確有貢獻需求，才研究獨立寫入端、資料保存與定時聚合；不先選雲端廠商、建立帳號系統、完整曲庫同步或媒體儲存服務。

## 5. 先解決資料語意，再決定資料庫

| 問題           | 決策要求                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 什麼算同一首   | 本機 `trackId` 不能直接當跨使用者歌曲 ID；作品、錄音版本、翻唱與伴奏來源可能不同。共同識別與人工修正須有可信度及不確定結果，不能只用檔名或來源 URL 強行合併。 |
| 計數代表什麼   | 明定播放／完成／練習、時間窗、同曲重播與循環上限，保留規則版本；不能稱為全市場或全民歡唱榜。                                                                  |
| 去重與隱私     | 去重、刪除請求與反灌票可能需要可關聯的憑證；持續識別碼或 hash 不自動等於匿名。先列清楚所需資料與限制，不能一面承諾完全匿名一面依賴永久追蹤。                  |
| 小樣本與冷啟動 | 標示期間、更新時間、參與範圍與統計口徑；設定最小樣本門檻與冷門列抑制。樣本不足時使用明標為編輯選曲的清單，不能冒充社群熱度。                                  |
| 錯誤與成本     | 離線／服務失敗不影響播放；需有批次大小、保留期限、請求限制、去重與重試邊界。估算寫入、查詢、聚合、下載流量及維運成本，不能只估資料庫容量。                    |

上述為產品與技術問題清單，沒有完成匿名性、安全性、資料來源使用條件或法規審查，也未選定 schema、廠商或反濫用演算法。

## 6. 建議順序與通過條件

1. 先確認三類非直播情境能否用現有核心完成準備、開唱與換曲；記錄卡點與設定步驟，不以新增功能數量當結果。
2. 延續既有逐曲設定 → A–B → 對時確認的規劃，另寫小份本機統計規格；不讓榜單中斷可靠性與既有手機方向。
3. 用少量編輯選曲／歌曲參照樣本驗證能否找到本機已有歌曲並加入待唱；未持有歌曲維持不可播狀態，不默默取得媒體。
4. 只讀選曲資訊確有使用價值後，再決定是否需要自願貢獻。先完成共同歌曲識別、計數口徑、資料流／同意與停止／刪除方案，再做有限雲端原型。
5. 有足夠樣本、品質與維運預算後才評估公開社群榜；歌唱評分與歌手競賽另作產品決策。

驗收草案：可離線完成核心任務；拒絕貢獻仍能讀榜；未同意時沒有統計上傳；迴圈／BGM 不放大榜單；未知歌曲不強制合併；低樣本不公布假熱度；服務失敗不阻擋本機播放。這些尚未實作或執行測試。

- 延伸研究見[串流、KTV 商業模式與資料架構](business-model-and-data-architecture-2026-10-26.md)：比較內容／場域／系統／資料服務的持續成本，補上歌曲身份、準備狀態與本機／讀榜／貢獻的候選邊界；未變更商業或實作承諾。
- 比較背景見[競品現況](competitive-research.md)與[播放器排練規劃](player-practice-planning-2026-10-26.md)。一般歡唱與練習的產品關係沿用該輪官方來源；本輪未實機操作 KAREOKIE，官網重新讀取失敗，未以其他網站補出新的功能／政策宣稱。
- 本機狀態依上列播放紀錄、播放安排契約與既有 source owners 核對；沒有查詢或上傳使用者實際曲庫。
- 受眾需求、榜單價值、使用意願與樣本門檻均為待驗證假設；沒有訪談、用量數據或商業可行性結論。
